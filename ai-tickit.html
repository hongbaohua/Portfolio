Tickit 是一個以 Prompt Engineering 驅動、用 Claude Code 開發的線上刷題 Web App。支援多使用者識別、跨主題與單元混搭出題、五種練習模式（含攻克模式與標記題反覆練習），作答完成後即時公布成績與弱點診斷；所有紀錄永久同步至 Supabase 雲端資料庫，換裝置也不遺失。

Prompt 策略：讓 Gemini 成為出題者

設計出題格式規範，讓 Gemini 輸出符合 parser.js 嚴格解析要求的 Markdown 題庫。
Gemini 出題的難點在於格式控制——題目、選項、答案、解析必須在同一份 Markdown 檔案中，格式嚴格符合 parser.js 的解析規則。第一次要求時格式不符（選項換行錯誤、分隔字串不一致），追加 Prompt 明確指定格式後才達標。Day 7 與 Day 12 刻意要求「將前期概念融合為商業情境題」，考驗情境理解而非單純記憶。

完成後上傳 GitHub，部署至 GitHub Pages（靜態網站，docs/ 資料夾）。

作答中完全不顯示對錯，避免「刷答」的心理干擾，真實模擬考場壓力，提升練習品質。全部完成送出後才公布成績。

遇到情境題組（共用前提的連續題）時，系統自動在題目上方顯示「上一題情境」卡片，確保作答時有完整的情境脈絡參考。

作答進度即時自動儲存至 localStorage，若中途關閉或離開，下次進入同一場測驗時自動從中斷處繼續，不必從頭作答。

題組保護邏輯

隨機抽題時，情境題（前後有邏輯關聯的題組）不會被拆散，確保上下文完整，維持沉浸式的作答體驗。

開發挑戰

CHALLENGE 01

Parser Regex Bug

問題 解析文字含數字條列（1. R/2），被 regex 誤判為新題號，導致 Q2 被切斷、整題消失。
解法 解析內的數字條列改為括號格式 (1)，不再觸發題號判斷 regex。
CHALLENGE 02

版面「數學正確但視覺偏左」

問題 側欄 fixed + 主內容 padding 補償，數學置中卻因右側剩餘區域偏移，視覺仍偏左。
解法 側欄改 sticky，整個 layout 以 max-width + margin: 0 auto 讓兩欄整體真正居中。
CHALLENGE 03

ERP 錯題模式篩選失效

問題 ERP 主題下錯題/攻克模式一題不顯示；資料庫有紀錄，卻因 topic 字串格式不一致全部篩選不到。
解法 統一 question_id 的寫入與查詢邏輯，確保兩端 topic 字串來源一致。
CHALLENGE 04

ERP 多選答案格式導致題目消失

問題 ERP 題庫含多選答案（(C)(D)/C/D），parser 無法解析，答案為 undefined，連帶造成 shuffleOptions 崩潰、整題消失。
解法 parser 補多選容錯（取第一字母）；shuffleOptions 格式不符時保留原順序而非崩潰。

過程反思

這個專案最大的收穫是親身體驗了「設計師如何用 AI 工具完成一個完整的軟體產品」——從需求定義、Prompt 策略、架構規劃，到每輪迭代的問題排查，都需要清晰的系統思維，而不只是會下指令。

Gemini 出題 + Claude Code 開發這樣的工具分工，讓我理解不同 AI 工具有各自的強項：Gemini 擅長創意發散與知識生成，Claude Code 擅長理解程式架構脈絡並精準修正。選對工具、給對 Prompt，才能讓 AI 真正發揮作用。

特別的是，整個開發期間我同時也是 Tickit 的第一個使用者——邊刷題備考、邊發現問題、邊疊加功能。★ 標記題目的書籤需求、攻克模式答錯後間隔幾題才重練的節奏感、考生管理頁登入後自動帶入帳號……這些設計決策不是推敲出來的，而是親身使用後「自然就知道缺什麼」。以真實的使用者體驗驅動功能與 UX 決策，比任何事先規劃都更直接也更準確。

2026 年 4 月，在以 Tickit 備考約一週後，正式通過「ERP 軟體應用師 — 配銷模組（SAP S/4HANA版）」認證考試。Tickit 不只是一件 AI 協作作品——它完成了自己被建造的任務，也驗證了「邊用邊做」這種開發方式的有效性。
