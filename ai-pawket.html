立即試用 Pawket
Pawket（喵喵財庫）是一個以貓咪為主題的財務管理 Web App，從無到有全程以 Prompt Engineering 驅動開發。整個過程分為三個階段：先以「30年投資理財專家」角色引導 Gemini 透過 16 輪問答完成功能架構決策，再以「20年 UI/UX 設計師」角色制定貓咪主題視覺規範，最後將完整規格 Prompt 交付 Google AI Studio 生成程式碼。App 整合 Gemini API 實現帳單 OCR 辨識，以吉祥物 Meowney 作為財務健康情緒指標。
2026 年 7 月 17 日起，Pawket 由 Claude Code 正式接手全面重啟。原型階段是用 Prompt 引導 AI Studio 一次性生成雛形；這個階段同樣是持續下指令、對話式驅動開發，但目標從「生出一個能展示的雛形」變成「打造一個資料庫化、能真實上線使用的產品」——重新設計帳戶模型、匯入並反覆查核真實記帳資料、建置對帳與商家智能辨識模組。是跟最初完全不同量級的工程投入，過程細節見下方。

Prompt 工程設計策略

角色設定：讓 AI 成為領域專家

這個專案使用了兩組核心角色設定，分別負責功能架構與視覺設計兩個維度。角色扮演的關鍵在於讓 AI 從「工具」轉化為「顧問」，使其在回答每個問題時都帶入專業立場與設計邏輯。 
【功能架構角色設定】
你是一位年資30年專業的投資理財專家，正在著手準備製作一個
「掃描對帳單後，並自動分類費用項目」的 app
現在正在 app 的研發初期，請用一次只問一個問題的方式，逐漸擴充完成這個 app 的功能

【UI/UX 角色設定】
你是20年經驗的網頁平面設計師，正在為這個專業財務 App 設計 UI/UX
請以客群為年輕女性為主，打造輕巧、活潑、可愛的元素氛圍
準確提供給 AI Studio 的 prompt

【命名決策】
重新命名財富貓咪，使其更有創意性（財富、貓咪基礎元素不變）
→ Gemini 提出 Purrse / Meowney / Pawket
→ 選定 Pawket（Paw + Pocket）、吉祥物命名 Meowney（Meow + Money）
「一次只問一個問題」的問答推進法

刻意在 Prompt 中限制 Gemini 的回應方式——每輪只問一個決策問題，強迫對話以遞進的邏輯展開。這讓每個功能決策都有清楚的原因，而非一次丟出大量模糊需求。共進行了 16 輪問答，涵蓋從資料模型到警示公式的完整架構設計。

核心公式：動態時間加權警示

由 Gemini 理財專家角色設計，這個公式解決了傳統記帳 App「月底才知道超支」的問題。以當月已過天數為基準，即時推算消費速率是否超出預算節奏。 
當前已花費 / 當月已過天數  >  當月總預算 / 當月總天數 × K（K = 1.15）

超標率 > 20%  → 🔴 Critical（紅色警示）
超標率 ≤ 20%  → 🟡 Warning（黃色警示）

例：月預算 $12,000，已過 15 天，已花 $8,000
當前日均：8,000 / 15 = $533
預算日均上限：12,000 / 30 × 1.15 = $460
超標率：(533 - 460) / 460 = 15.9%  → Warning

App 三頁面架構

① 貓咪指揮中心（Dashboard）

核心儀表板，以 Meowney 吉祥物情緒指標（Smile / Meh / Frown）呈現當前財務健康狀態。包含動態時間加權警示、DTI 償債比率、財務結構圓餅圖（固定/變動/投資）、潛在財富機會試算（變動支出投入 7% 年化報酬 10 年後獲利估算）、夢想目標進度條（4 段動畫：種子→成長→衝刺→豐收）、異常消費偵測、季節性支出熱圖，以及 PDF 報告匯出。
② 餵食帳單 Scanner

上傳銀行或信用卡帳單截圖，Gemini API 自動執行 OCR 辨識，智能區分收入與支出，標記三級分類。Prompt 設計採「主表優先原則」避免摘要欄位重複計算，並加入指數退避重試機制（最多 3 次，1s → 2s → 4s）。
③ 罐罐明細本（交易明細）

全文搜尋、L2+L3 標籤篩選、拆帳（分裝）功能（含 Undo 5 秒復原）、批次修正相似交易、JSON 匯入/匯出備份、手動新增交易。三級分類體系（L1 → L2 → L3）讓支出可以細緻追蹤到「咖啡」而非只有「餐飲」層級。

開發挑戰：AI Studio 的無法復原限制

Google AI Studio 的對話是覆蓋式的——每次修改都直接覆蓋前一次的程式碼，沒有 Undo。這導致「修好一個功能，後續對話又把其他功能改壞」的情況反覆發生。應對策略是在每次重大修改前手動另存一個新版本資料夾，最終累積了 9 個版本。
版本主要更新
v1.1初始雛形，基本三頁框架
v2.1UI/UX 重構，導入貓咪主題視覺
v3.2新增夢想目標功能、標籤系統
v3.3統一頁面命名、新增快速查找
v4.2首頁分析邏輯修正
v4.3目前最新版本，多項 Bug 修正；Claude Code 接手後持續優化
版本演進中最難解決的問題是夢想目標進度條邏輯錯誤：原本的加權公式（70% 存款進度 + 30% 時間進度）導致「還沒存任何錢但快到期時，進度條自動顯示 24%」的誤導性結果。此問題在 Claude Code 接手後，透過直接閱讀 logicService.ts 找到根因，將 weightedPercent 改為直接等於 financialPercent（實際存款比例）才得以修正。

過程反思

這個專案最大的收穫是驗證了「Prompt Engineering 作為產品設計方法」的可行性——透過角色設定和問答式推進，讓 AI 扮演理財專家完成了一份紮實的功能規格書，而不是讓設計師憑空想像功能需求。16 個決策點的問答過程，其實就是一份結構化的產品思維文件。

AI Studio 的無法復原限制則是一個重要的課題：它讓我學到「AI 生成工具的使用策略」和「版本管理的必要性」。每次修改前先備份、每個 Prompt 都要明確指定範圍，是降低風險的關鍵。

最後接手 Claude Code 修正 Bug 的過程，讓我體驗了不同 AI 工具在同一個專案中各自扮演的角色——Gemini 適合發散思考與規格設計，AI Studio 適合初始程式碼生成，Claude Code 適合精確的除錯與邏輯修正。三者組合，才是完整的 AI 輔助開發鏈。

從原型到產品：底層整個重建

AI Studio 原型完全沒有資料持久化能力——重新整理頁面，剛剛記的帳就消失了。重啟的第一件事是接上 Supabase（Postgres + Auth），讓資料真的存得住，而且是「我的資料只有我看得到」（資料表全部開啟 Row Level Security）。接著重新設計帳戶模型：現金、銀行簽帳卡、電子支付錢包、實體儲值卡各自是一個「碗」，每一筆交易都要說清楚錢是從哪個碗裡出去的；餘額不是手動輸入的數字，而是從每一筆交易即時加總出來的結果。

功能命名系統：養貓主題

資料庫、帳戶模型這些底層架構穩定後，回頭處理一個純設計層面的問題：功能一個個加上去，介面文字卻是隨手取的技術名詞（對帳、帳戶管理、應收應付……），跟「喵喵財庫」這個品牌調性完全脫節。跟 Claude Code 腦力激盪、來回調整幾輪後定案一個世界觀：「使用者使用＝餵食，餵飽貓咪後，貓咪才會工作」，延伸出「餵食」「碗」兩條命名主線，統一改寫全站使用者看得到的文字——刻意只改介面文字，不動程式內部的變數／元件／欄位名稱，把改名的風險範圍壓到最小。

貓咪指揮中心：一頁看完財務狀況

首頁不是把數字排出來就好，而是回答幾個真正會影響決定的問題：這個月還好嗎？手上的錢還能撐多久？哪一類花超過了？想買的東西買得起嗎？每張卡片對應一個問題，而且所有門檻與基準都可以追溯到「使用者自己設定過的數字」或「自己的歷史紀錄」，不是系統憑空猜的。
同一份資料、三種情緒

情緒指標的三種狀態不是隨機的表情變化，而是同一套判斷在不同預算設定下的結果。下面三張是完全同一個月的資料，只改了「分類月預算」這一個變因——這也是刻意的設計：警示的基準必須是使用者自己確認過的數字，系統不自己猜，所以同樣的花費，在不同人的預算標準下本來就該得到不同的提醒。

罐罐明細本：每天真的會用的那一頁

明細本是使用頻率最高的頁面，設計重點是「一列就看完一筆帳的全部資訊」，不用點進去才知道自己買了什麼。

記一筆帳：真實生活比「一個金額」複雜得多

真實的一筆消費常常不是單純的「商家＋金額」：有折價券、有好幾樣品項、有套餐、有外幣、有時候是幫別人買的、有時候一張發票要分給好幾個預算分類。新增／編輯表單把這些情境全部收進同一張表單，但用摺疊分層，平常只要填三個欄位就能存檔。

幫別人先付的錢：分帳與往來追蹤

代購、代墊、借錢給朋友這些錢，會讓記帳變得很尷尬：錢確實離開了戶頭，但它不是「我的消費」。Pawket 的處理方式是把兩件事分開——現金流照算，消費分析不算。借出跟收回可能相隔當天、好幾天、甚至跨月，現金流要看得出錢包真實的凹陷與回填；但這些金額一旦混進消費分析，分類佔比、超支警示、燒錢速度就全部失真。

餵食核對：跟銀行月結單互相核對

上傳銀行月結單 PDF，跟自己記的帳互相核對，找出漏記、重複或金額打錯的項目。刻意不比對商家名稱——銀行代碼常常是截斷、無意義的字串——而是用「日期區間＋金額」比對：每個帳戶可以各自設定預期入帳延遲天數（例如簽帳卡 1～3 天），消費日與入帳日差在範圍內就算對得上。實際使用後還補上兩個真實世界的狀況：銀行會把同一期帳單拆成多份 PDF 寄發（改成支援一次上傳多份合併比對），以及銀行把同一筆消費拆成兩列印出（改成會嘗試把同一天的兩列加總起來比對）。
商家智能辨識三層架構

銀行帳單上的商家代碼常常是同一間店、每次代碼卻略有不同的截斷字串。設計了三層判斷：先做免費即時的模糊比對（跟已知商家名稱做相似度比對），信心不足時交給 Gemini 判斷最可能對應哪個已知商家，兩層都不確定才問使用者本人——確認後存成新的商家對照紀錄，下次同類代碼出現就不用再問。對照表也刻意不是「一個代碼＝一個商家」，而是候選清單：實測發現近兩成代碼背後其實對應過兩種以上不同用途（例如同一組 Google Play 代碼背後可能是好幾款不同遊戲），只有候選剛好一筆時才自動帶入。

喵喵心願罐：不是存錢進度，是排隊清單

心願罐刻意不做成「存錢進度條」。這個 App 的本質是記帳，使用者並沒有真的把錢撥到另一個罐子裡——錢就是帳戶餘額本身。所以心願罐追蹤的是「排隊順序」：可動用餘額扣掉排在前面還沒買的項目，才知道排後面的還差多少，並用最近幾個月的平均淨現金流推估「照這個速度大概什麼時候買得起」。

戰情報告：讓 AI 真的讀資料、寫一份看得懂的解讀

這個功能原本叫「匯出報告」，做法是把畫面圖表截圖拼成 PDF——看起來像報告，但它沒有「解讀」。改版後改成：把首頁已經算好的統計數字（分類加總、配速警示、異常偵測、固定週期性支出），加上資料量不大時的逐筆明細，一起交給 Gemini 寫一份白話的整體評語、重點摘要、異常發現與建議。每份報告都會存進資料庫，可以回頭看、重新下載，不用重複消耗 AI 額度。

系統設定：把「基準」交回使用者手上

這個 App 有很多會主動跳出來的警示，而警示最怕的是「基準是系統自己猜的」——猜錯一次，使用者就再也不相信它。所以所有門檻都收進系統設定由使用者自己確認：分類月預算、長期預留支出（年繳保費、稅金這種大額低頻支出的月均攤）、每個帳戶的入帳延遲天數。系統只負責提供「近 3 個月」與「全部歷史」兩個參考數字，不會自己填進去。

手機版：真正記帳的場景在手機上

記帳幾乎都發生在剛結完帳、站在店門口的那一刻，所以手機版不是桌機版縮小，而是重新排過：導覽從側欄改成頂部橫列、表格改成卡片式堆疊、新增交易改成四步驟的引導式表單，每一步只問幾個欄位，不用在小螢幕上面對一整張長表單。

真實資料匯入與資料品質查核

資料庫接上後，下一步是把真實記帳資料匯入系統——這一段的重點不是「匯進去」，而是「匯得對」。分類邏輯採三層判斷：優先比對既有的人工標註紀錄，比對不到的用商家關鍵字規則庫分類，兩者都不行才需要人工確認。匯入完成後並不是結束，而是接著進行一輪完整的資料品質查核：金額與日期逐筆覆核、商家分類逐一覆核，過程中實際抓到並修正了好幾個真實的資料錯誤與分類判斷失誤。
不是做完就結束，是建立一套持續驗證的流程

比起「一次性匯入」，這個階段更像是在建立一套可以重複執行的資料驗證機制——每次發現新的資料品質問題，就把它變成下一輪查核的檢查項目，逐步把「資料看起來是對的」提升到「資料真的是對的」。持續驗證的成果：其中一個帳戶後來重新下載完整銀行歷史明細、逐筆核對超過 800 筆交易，最終跟正式對帳單的落差收斂到 $0。

開發挑戰

部署卡在 95 天前的舊版本

正式重啟上線後，發現線上網址其實還停留在一個更早、完全沒有登入功能的版本——原因是 Vercel 專案當時沒有接上 GitHub 自動部署，push 到 GitHub 並不會觸發重新部署。排查後手動重新部署，並完整接上 Git 自動部署整合，確保之後每次 push 都會自動更新線上版本。
資料庫權限意外查核

用查詢工具檢查資料時，意外發現資料庫裡還留有幾筆早期測試帳號的殘留資料。雖然 Row Level Security 已經確保使用者彼此看不到對方資料，但這次順勢建立了一套「新的查詢能力只做讀取、任何寫入都必須先產出 SQL 由本人確認執行」的把關流程，把資安意識落實到日常工作習慣裡。
AI API 額度限制下的容錯設計

大量歷史交易需要重新做語意判斷分類，但 Gemini API 免費額度有嚴格的每日請求上限，很快就撞到上限。改為分批處理＋進度存檔（中斷可從上次進度接續），額度用盡時則切換由 Claude 直接判斷，確保整個流程不會因為單一 API 限制而卡住。
用螢幕錄影救回沒有其他來源的資料

某個電子支付帳戶的消費紀錄查無其他來源，交易清單又長到一張張截圖太麻煩，改用手機螢幕錄影記錄捲動過程。這台機器原本沒辦法直接理解影片內容，裝上開源影像處理工具後，試了幾種「自動判斷畫面停在哪裡該存」的方法都不夠穩定，最後改採最簡單可靠的做法：固定每秒擷取一張畫面、多張疊成一張長圖，雖然檔案數較多，但保證不漏看任何一段內容，再逐張人工核對整理成正式交易紀錄。
統計口徑不一致：同一筆錢在兩張卡片上被算了兩種樣子

「幫別人先付的錢」這件事踩過一個很隱晦的坑：花出去那一筆因為標了「代購／代墊／借貸」而被排除在統計外， 但對方還錢時自動產生的那筆收入卻沒有被排除，於是淨現金流憑空多出一筆收入；同一時間， 「還錢給別人」又被算進「社交人情」的消費裡，還會觸發超支警示。 釐清後定下一條明確規則：錢真的有進出戶頭 → 現金流照算；但那不是你的消費 → 所有消費分析一律排除， 並把這條規則收斂成一個共用判斷，讓分類比率、支出排行、配速警示、燒錢速度、預算建議全部套用同一套標準。
會自己失效的設定：按了儲存，重新整理就變回預設值

全面體檢介面時發現，首頁齒輪裡的「結算日」與「超支扣零食」兩個設定只存在瀏覽器記憶體裡—— 按下儲存看起來有效，重新整理就默默變回預設值。修正時又踩到第二個坑： 兩個設定分成兩次寫入使用者資料，兩次請求互相競爭，結果只有其中一個存得起來， 最後改成同一次寫入。另外也發現「超支罰則」比對的是一份早就沒有任何畫面可以修改的預設預算， 門檻永遠停在舊數字、正常生活一定超支——改成比對使用者自己設定的分類月預算總和，沒設定就不啟動。
真實使用才會浮現的邊界案例

對帳模組上線後，實際拿真實對帳單試用時發現部分交易一直被誤判成「系統記了、但銀行對帳單沒有」，追查後才發現是銀行把同一期帳單拆成兩份 PDF 寄發，當時只上傳了其中一份。這類問題只有在真實使用情境下才會浮現——這也是這個階段跟原型階段最大的不同：不是把功能做出來就結束，而是要持續跟著真實使用回饋修正。

過程反思

這次重啟讓我體會到「AI 生成的原型」和「可以每天真實使用的產品」之間，中間還有一大段距離——資料要能安全存起來、金額計算邏輯要禁得起真實使用情境的檢驗、部署與版本控管要穩定可靠，這些都是原型階段不會遇到、卻是產品上線後每天都要面對的課題。

兩個階段其實都是「用 Prompt／指令驅動 AI 開發」，差別不在有沒有用 Prompt Engineering，而在指令的顆粒度跟工程的性質完全不同：原型階段是一次次用結構化 Prompt 換取一整塊新功能；這個階段更常是針對某個具體問題（一個 bug、一筆錯誤資料、一個安全疑慮）下達精確指令，跟 Claude Code 一起診斷根因、驗證修正、確認不影響其他功能，再決定是否上線。這是「與 AI 一起維運一個真實在用的產品」所需要的能力，跟第一階段同樣重要，只是形式不同。

最近一次的全面介面體檢又補上了第三種能力：主動去找還沒有人抱怨的問題。 沒有人回報「設定存不起來」，是因為那個功能本來就沒人在用；沒有人發現統計口徑不一致， 是因為兩個數字剛好在多數情況下互相抵消。這些問題不會自己浮上來， 要靠有意識地逐一檢查每個畫面、每段文案、每個算式，才會被翻出來—— 而這也是 AI 協作最需要人來把關的部分：AI 可以很快把功能做出來， 但「這個數字到底代表什麼、使用者會不會誤解」始終要有人負責定義。
